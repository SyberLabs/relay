## Task 2: select saved facts for a version-bound assistant handoff — remaining

**Problem:** Profile already persists verified facts, but Connections requires typing supplied facts into an unsaved text box each time. Its current packet binds the job/version, not a chosen subset of saved facts or their profile version.

Assistant context-reading work in [PR #100](https://github.com/SyberLabs/relay/pull/100) is separate from this explicit Connections picker and its selected-fact snapshot/return validation. Do not treat context availability alone as completion of these criteria.

**Result:** with one selected job, the person chooses an explicit subset of their usable saved facts, reviews the exact outgoing context, and hands it to an external assistant. A returned draft can be staged only against the job and fact context that authorized it; acceptance remains a separate human action.

Acceptance scenarios:

1. Connections offers the signed-in user's saved facts with readable claims and selection controls. Only Verified, unexpired, non-retired facts can be selected, using existing `usableFact` semantics. Proposed/expired/retired facts are excluded or disabled with an explanation. Nothing is selected by default and no other user's facts can appear. Selected IDs are checked server-side against the authenticated owner; client-supplied verification labels are not authority.
2. With no usable facts, show a direct path to Profile to add/verify facts and preserve the selected job when returning. Do not prefill invented facts or reinterpret job research as verified applicant claims. The saved-fact handoff requires at least one deliberate selection. A generic legacy handoff, if retained, must not acquire a saved-fact verification claim.
3. Before explicit copy/download, show the exact content to be shared: job identity/version, selected fact claims, existing draft if included, and explicitly chosen research/task instructions. Allow deselection. Do not include unselected facts, the full resume, evidence attachments, unrelated jobs, or private profile metadata by default. Internal fact identifiers and version binding may travel as machine metadata; unnecessary evidence text does not. No automatic send or account connection.
4. Selecting a fact uses its saved claim without retyping or silent rewriting; handing off for another job lets the user choose the relevant subset again without reconstructing facts. Preserve the underlying saved facts across reload. Reset or explicitly reconfirm outgoing selection when changing jobs so context is not silently shared with a different target.
5. Freeze a handoff snapshot containing existing job ID/key/version plus selected fact IDs, exact selected claim snapshots, and current profile version. Reuse the existing profile version as the conservative invalidation boundary. The result must echo or otherwise resolve to that same immutable context; edited IDs, missing required binding, wrong owner, or altered fact snapshot cannot be accepted as the original handoff. An external assistant cannot refresh a version number to make old work current. Use the smallest compatible packet/result extension; document legacy behavior without labeling an unbound packet verified.
6. Revalidate on handoff creation and before persisting its returned draft: job still matches, profile version is current, selected facts still belong to that user and remain usable, and exact claims match the snapshot. If the profile changed (including an unrelated profile edit under the conservative rule), a selected fact expired/retired/changed, or the job changed, reject stale work with a clear request to review a fresh packet. Preserve the user's visible newer work; do not overwrite it. Profile/job changes between checks and save must be rejected rather than winning a race. Fact expiry must be checked at return even without a profile-version increment.
7. Copy/download failure leaves choices visible for retry. Loading/pasting a valid returned result stages wording for review without saving, accepting, changing application status, or sending. Persistence requires a human save or exact-acceptance action; acceptance must be explicit, never a side effect of importing or ordinary saving. The acceptance action may also save, avoiding a redundant required click. Return validation does not establish that every generated claim is true. Existing citation gates on agent-log paths remain in force and are not bypassed by labeling handoff text verified.
8. Exact acceptance belongs to the persisted words/version. After acceptance, changing one character or receiving another draft requires fresh review. Unsaved editor changes, changing job selection during file loading, stale editor versions, and session expiry retain existing protections. Saved-fact work must not reset Submitted/Live loop/terminal status to enable acceptance. Current fresh-acceptance limits for active follow-ups remain visible in the pilot; resolving them is a separate product decision, not permission to expand this task silently.
9. Verification evidence: two fictional usable facts selected from a mixed-state ledger, unselected sensitive fixture omitted from serialized output, reload/reuse on a second job, no-facts path, copy failure, wrong owner/ID/version, profile edit and expiry while the assistant is working, concurrent save conflict, valid return staged without acceptance, accepted-text edit invalidation, and sign-out during a pending operation. Verify both the user-visible preview and serialized payload match the chosen subset. No live assistant or telemetry implementation is required for deterministic checks; a separate assisted transport check is QA, not pilot success.
