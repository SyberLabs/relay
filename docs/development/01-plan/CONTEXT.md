# 01 — Plan

Inputs: the user's outcome, the issue, root contracts, abuse controls, delivery rules, and the smallest relevant source slice from the parent router. Read current official provider documentation only if the proposal depends on that provider. Do not load the product research library for an ordinary code task.

Question each proposed requirement and name its owner. First remove unnecessary behavior, then simplify what remains. Identify one testable outcome, the existing behavior, the smallest change, exclusions, and a failure-path check. Inspect existing implementation before proposing a new service, abstraction, agent, or dependency.

For any expensive operation, record admission, input/storage/work bounds, retry and failure behavior. Relay-funded upstream or background work requires the currency-budget controls in the authoritative abuse document before release.

Output: a concise issue-linked plan with acceptance criteria and affected paths, or an update to the existing plan. Record unsettled assumptions and the next action in a checkpoint only if work must resume later.

Review boundary: continue authorized implementation when scope is concrete. Clarify a material missing requirement; this folder adds no approval ceremony. Peer merge review and production approval remain separate later gates.
